# Demo Code Collection

A collection of classic **old-school graphics effects** implemented in **C++20** using **SFML**.

The project recreates several techniques associated with DOS-era graphics programming and the demoscene: palette-based fire propagation, plasma generated from trigonometric functions and animated through palette cycling, and the classic XOR pattern.

Rather than relying on shaders or high-level drawing primitives, the effects are generated directly in software by manipulating pixel and palette data.

## Demos

The repository currently contains three effects:

- **Fire** — procedural fire generated by propagating and averaging intensity values through an indexed framebuffer
- **Plasma** — a sinusoidal plasma field animated through palette cycling
- **XOR Pattern** — a classic bitwise XOR visualization generated directly from pixel coordinates

All three demos share a common 320 × 200 software-rendering framework.

## Why 320 × 200?

The demos use a logical resolution of 320 × 200. This was one of the characteristic graphics resolutions of DOS-era VGA programming, particularly the 256-color Mode 13h display mode.

Mode 13h provided a simple linear 64,000-byte framebuffer and a 256-entry color palette, making it particularly well suited to software-generated effects.

This project recreates that style of graphics programming with modern C++ and SFML:

```text
Classic approach              This project
────────────────────────      ────────────────────────
320 × 200 framebuffer    →     320 × 200 texture
8-bit pixel indexes      →     index buffer
256-color palette        →     sf::Color palette
VGA framebuffer writes   →     RGBA pixel buffer
display refresh          →     SFML texture update
```

SFML handles the platform-specific window and display operations while the effects themselves remain software generated.

## Architecture

The three effects derive from a common `DemoApp` base class.

```text
                    ┌─────────────┐
                    │   DemoApp   │
                    └──────┬──────┘
                           │
             ┌─────────────┼─────────────┐
             │             │             │
             ▼             ▼             ▼
        ┌─────────┐   ┌──────────┐   ┌─────────┐
        │FireDemo │   │PlasmaDemo│   │ XORDemo │
        └─────────┘   └──────────┘   └─────────┘
```

`DemoApp` provides the common graphics infrastructure:

- 320 × 200 logical resolution
- 256-entry color palette
- indexed pixel buffer
- RGBA output buffer
- SFML texture and sprite
- full-screen rendering
- 60 FPS frame limiting
- event processing
- animation loop

Each derived class implements its own `animate()` function to generate or update the effect.

This keeps the platform and presentation code separate from the algorithms responsible for producing the graphics.

## Software Rendering Pipeline

The animated effects use a two-stage representation similar to traditional 8-bit indexed graphics.

```text
┌─────────────────────┐
│  8-bit pixel index  │
│       buffer        │
└──────────┬──────────┘
           │
           │ lookup
           ▼
┌─────────────────────┐
│ 256-entry RGB/RGBA  │
│       palette       │
└──────────┬──────────┘
           │
           │ expand
           ▼
┌─────────────────────┐
│ 32-bit RGBA pixel   │
│       buffer        │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│    SFML Texture     │
└─────────────────────┘
```

Each logical pixel can therefore be represented by a single 8-bit value selecting one of 256 colors.

Before presentation, the indexed image is expanded through the palette into the RGBA buffer expected by the SFML texture.

This separation between **pixel intensity/index** and **display color** is central to both the fire and plasma effects.

# Fire

The fire demo implements a classic procedural software-fire effect.

A row of random intensity values is generated along the bottom of the framebuffer:

```text
low intensity                         high intensity
     0  ───────────────────────────────► 255
```

For each pixel above that row, a new intensity is calculated using neighboring pixels beneath it:

```text
        destination
             ▲
             │
        ┌────┼────┐
        │    │    │
        ▼    ▼    ▼
      left center right
           below
             │
             ▼
        two rows below
```

Conceptually:

```text
new intensity =
    (left below
   + center below
   + right below
   + center two rows below)
   / decay
```

The implementation uses a divisor slightly greater than four so that energy gradually decreases as the calculated values propagate upward. The result is the characteristic rising and fading appearance of flame.

Horizontal coordinates wrap around the framebuffer, avoiding special edge cases at the left and right boundaries.

## Fire Palette

The fire effect uses a 256-entry palette that progresses through several color ranges:

```text
black → dark red → orange → yellow → white
```

The lower portions of the palette are constructed incrementally. The upper range uses C++20 `std::lerp()` to interpolate toward white.

The fire algorithm operates only on palette indexes. Color is applied afterward when the indexed framebuffer is expanded into RGBA pixels.

This separates the simulation of **heat intensity** from its visual representation.

# Plasma

The plasma demo generates a static two-dimensional field using sine and cosine functions.

For each `(x, y)` coordinate, an index value is calculated from a combination of:

```text
cos(x × 0.1) + sin(y × 0.1)
```

The result is scaled into the range of the 256-entry palette.

Conceptually:

```text
               sine along Y
                    │
                    ▼
             ~~~~~~~~~~~~~~~
            /               \
           /                 \
          +                   +
         cosine along X
                  │
                  ▼
           resulting plasma
                field
```

Once generated, the underlying field does not need to be recalculated every frame.

Instead, animation is produced by rotating the palette:

```text
Frame 1:
[A B C D E F ...]

Frame 2:
[B C D E F ... A]

Frame 3:
[C D E F ... A B]
```

The same pixel indexes therefore map to different colors over time.

This technique—**palette cycling**—was especially useful on indexed-color hardware because animation could be produced by changing palette entries rather than rewriting the underlying image.

## Plasma Palette

The plasma demo uses a 256-entry grayscale palette:

```text
black → white → black
```

The first half progresses from black to white, and the second half mirrors the first back toward black.

Each animation frame rotates this palette by one position and expands the unchanged index buffer through the newly shifted colors.

# XOR Pattern

The XOR demo is the simplest effect in the collection and demonstrates how visually complex patterns can emerge from elementary bitwise operations.

Each pixel value is calculated directly from its coordinates:

```cpp
value = (x ^ y) & 0xFF;
```

where `^` is the bitwise exclusive-OR operation.

That value is written equally to the red, green, and blue channels:

```text
R = value
G = value
B = value
```

producing a grayscale image.

No textures, source images, trigonometry, random numbers, or simulation are required. The entire pattern emerges from the binary relationship between the `x` and `y` coordinates.

This is a useful visual example of how simple integer and bitwise operations can produce complex structure.

## Shared Demo Framework

The `DemoApp` class provides the reusable application loop for the effects.

At startup it creates:

```text
256 palette entries

320 × 200 = 64,000
indexed pixels

320 × 200 × 4 = 256,000
RGBA bytes
```

It then creates an SFML texture representing the 320 × 200 logical framebuffer and displays it through a sprite.

The application itself runs full screen while SFML scales the logical view to the host display.

The main loop follows a conventional real-time graphics structure:

```text
┌──────────────────┐
│  Process Events  │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ Update Animation │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│   Clear Window   │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│   Draw Sprite    │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ Display Frame    │
└────────┬─────────┘
         │
         └──────────────► repeat
```

Rendering is limited to 60 frames per second.

## Modern C++ Elements

Although the effects are intentionally inspired by older graphics techniques, their implementations use modern C++ facilities.

Examples include:

- C++20
- `std::vector`
- range-based loops
- `std::generate`
- `std::rotate`
- `std::reverse_copy`
- `std::lerp`
- `<random>` facilities
- uniform initialization
- `constexpr`
- inheritance and virtual functions
- Microsoft GSL index types

The result is a useful contrast between algorithms associated with early PC graphics programming and contemporary C++ implementation techniques.

## Requirements

The project requires:

- CMake 3.17 or later
- A C++20-compatible compiler
- SFML 2.5
- Microsoft Guidelines Support Library (GSL)

The SFML components used are:

```text
system
window
graphics
```

The project was originally tested on macOS 10.15.7 using:

- Visual Studio Code
- Xcode Command Line Tools 12.4
- Homebrew

Other platforms supported by SFML and the required C++ dependencies may also work, but were not part of the original tested configuration.

## Building

Clone the repository:

```bash
git clone https://github.com/foxrunlabs/democode.git
cd democode
```

Create a separate build directory:

```bash
mkdir build
cd build
```

Configure the project:

```bash
cmake ..
```

Build all three demos:

```bash
cmake --build .
```

Each demo is built as a separate executable:

```text
fire
plasma
xor
```

## Running the Demos

After building, run the desired executable from the build tree.

For example:

```bash
./fire/fire
```

or:

```bash
./plasma/plasma
```

or:

```bash
./xor/xor
```

Each application runs full screen.

Close the window to exit the demo.

## Design Highlights

Although these are deliberately small programs, the collection demonstrates several graphics and software-development concepts.

**Direct pixel manipulation**  
The effects are generated algorithmically rather than assembled from sprites, images, or high-level graphics primitives.

**Indexed-color graphics**  
The fire and plasma effects separate pixel values from their displayed colors through a 256-entry palette, reproducing an important technique from early PC graphics hardware.

**Palette animation**  
The plasma demo shows how changing the interpretation of existing pixel data can produce animation without regenerating the underlying image.

**Procedural graphics**  
The fire effect emerges from a simple iterative propagation algorithm, while the XOR image is produced entirely from pixel coordinates.

**Bitwise operations**  
The XOR demo provides a direct visual representation of bitwise computation.

**Real-time graphics**  
The common framework implements a conventional update-and-render loop operating at up to 60 FPS.

**Separation of concerns**  
A common `DemoApp` base class handles window management and presentation while each derived class contains only the algorithm required for its particular visual effect.

**Modern implementation of historical techniques**  
The project combines techniques associated with DOS/VGA-era software rendering with C++20, SFML, CMake, and contemporary standard-library facilities.
